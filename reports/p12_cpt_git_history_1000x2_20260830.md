# P12 source-native Git-history CPT 1,000×2

Date: 2026-08-30

## Outcome

The replacement v2 local-probe batch retained 1,000 exact-tokenizer 64K rows
and 1,000 exact-tokenizer 128K rows. It contains 192,776,946 Qwen context
tokens: 64,390,502 in the 64K band and 128,386,444 in the 128K band. The
independent audit passed after recomputing every context length and
reconstructing every training row.

This is a source-native continued-pretraining candidate, not an executable SFT
release. It is also not 2,000 independent worlds: the rows are 2,000 disjoint
windows from two public repository histories (`dprint/dprint` and
`astral-sh/ruff`).

## Source and filtering accounting

- 17 signed, verified source manifests
- 277,945 accepted source-body-unique records in those manifests
- 259,861 used source records across retained windows
- zero source-record reuse across windows or length bands
- zero exact context duplicates
- zero exact source-record-body duplicates
- 11,153 exact duplicate source bodies rejected before packing
- 7 credential-shaped commits rejected fail-closed
- 90 candidate windows rejected for QA/chat prompt contamination
- 2,000 training rows reconstructed exactly from the signed CPT rows

Duplicate removal does not bridge around a removed body. It creates a new
source component, so the packer cannot manufacture a dependency across missing
text.

## Length and event-growth review

The 128K rows genuinely contain more source records than the 64K rows: median
record counts are 169 versus 85, and means are 173.13 versus 86.73. Median
context bytes are 400,650.5 versus 201,922.

However, source records are patch chunks, not always distinct workflow events.
The median number of distinct commits is one in both bands. There are 569
single-commit 64K rows and 518 single-commit 128K rows; mean distinct-commit
counts are 5.93 and 11.29. Median calendar span is zero days. A large authentic
commit can therefore supply a long, coherent code document without supplying
long-time evolution.

This distinction is release-critical: v2 satisfies the requested volume for
real source-native long-document CPT, but it does not satisfy the project's
stronger long-duration, multi-release workflow objective for every row.

## Trust and permitted use

The audit has a report-role local-probe signature and binds the release,
source, CPT, training, and tokenizer hashes. The run deliberately remains
`train_ready=false` and `production_eligible=false`. The source and report roles
were isolated by the probe runner but used combined local diagnostic trust, not
independent KMS-backed asymmetric approval.

The candidate is suitable for controlled local CPT ablations with the above
classification. It must not be described as a production release, a 2,000-world
corpus, or an executable SFT set, and it is not authorized for the qualified HF
dataset.

Additional limitations are current-HEAD rather than per-historical-commit
license verification, exact rather than semantic near-duplicate filtering, two
code-domain repositories only, and no counterfactual/answer program.

## Next gate

The longitudinal successor should require independent source events in every
window (initial target: at least 8 commits for 64K and 16 for 128K), report
calendar/release-cycle span, and add source-native release and dependency
relations. Capacity should then be replenished from the existing uv and
Wasmtime caches and from SEC, OpenReview/arXiv, Wikimedia/KB, regulation,
cybersecurity, clinical, finance, and visual/game production workflows. Those
rows must remain a separate product from executable SFT, whose CF, remove-one,
retrieval, semantic-growth, and strict-replay gates still apply.
